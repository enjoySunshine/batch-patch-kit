# 2000 人横坐标迁移 — 增量序列化基准

地图上放 2000 个人，每人初始坐标 `(x=10, y=20)`。整包全量同步一次（不计时），
随后把每个人的横坐标改成 `15`，纵坐标 `20` 全程不动。只对后面这 2000 次修改计时、计字节。

## 预算（仅计全量同步之后的部分）

| 指标 | 预算 |
| --- | --- |
| 编码 + 解码 | ≤ 400 ms |
| 实际发出的字节总和（缓冲未用部分不计） | < 200,000 |
| 解码结果 | 所有人 `x=15, y=20`；纵坐标不允许变化 |

## 失败形态的根因

题目描述的 39,750 字节/包、总计 7950 万字节，等价于**每次只改一个字段，却把整份状态
重新全量编码一遍**（`encoder.encodeAll()` 每拍调用）。本仓库实测复现（`experiments/bad-mode.mjs`）：

```
REF. full snapshot re-encoded per change:
  packet size: 37,750 bytes (constant)   × 2000 包
  total: 75,500,000 字节
  encode only ≈ 3.1 s,  encode+decode ≈ 8.3 s
```

全量包大小取决于容器和键：`ArraySchema` 全量 28,860 B，`MapSchema` 数字字符串键全量
37,750 B，9 字符键 48,860 B——都在题目里 39,750 这一量级。包大小和改没改、改谁无关，
因为每一包写的都是整份 2000 人的坐标。这与缓冲大小无关：把 `Encoder.BUFFER_SIZE` 调到
256 KB 后，全量编码的长度不变。

## 正确做法：增量补丁（`encoder.encode()` + `discardChanges()`）

增量编码只把“这一拍真正变过的字段”写进包里。以 `MapSchema` 为例，第一个人的首包只有
**4 个字节**：

```
[255, 2, 128, 15]
  │    │   │   └─ 新值 x = 15
  │    │   └───── OPERATION.ADD(128)，字段索引 0（即 x）
  │    └───────── 目标对象的 refId（player[0]）
  └────────────── SWITCH_TO_STRUCTURE：切到那个对象再写字段
```

refId 增大后变长 1~2 字节，所以 2000 个补丁的实际分布是
`4B ×126, 5B ×128, 6B ×1746`，合计 **11,620 字节**。

## 两种被题目接受的交付形态（`src/benchmark.mjs` 都实现了）

- **方案 A：一人一包**。2000 个小补丁按顺序编码、按顺序解码。第一包解完
  `player[0].x = 15`，还没轮到的人仍是 `10`；2000 包解完所有人 `x=15`。
- **方案 B：2000 次修改并成一包**。一次 `encode()` 输出包含全部 2000 个字段变更的单个
  11,620 字节补丁，另一边一次解码直接看到最终结果，中间没有那些 `10`。

两种形态的字节总数相同（11,620），因为线上字节只取决于“有多少字段变了”，与打包次数无关。

## 实测结果（best of 3，Node 22）

| 方案 | 包数 | 发出字节 | 编码 ms | 解码 ms | 合计 ms | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| A 一人一包（增量） | 2000 | 11,620 | ~3 | ~6 | **~9** | PASS |
| B 合并一包（增量） | 1 | 11,620 | ~0.4 | ~0.8 | **~1.2** | PASS |
| 参考：每拍全量重编码 | 2000 | 75,500,000 | ~3100 | ~5200 | ~8300 | 失败形态 |

距预算余量：时间约 45~300 倍，字节约 17 倍。

## 计数与计时口径

- 字节按 `encoder.encode()` 返回的 `subarray` 的实际长度累加；256 KB 后备缓冲里没用到的
  尾部不计（题目明确“空着的缓冲不算进那 20 万”）。
- 全量同步那一拍单独测量、打印，但不参与 400 ms / 20 万字节预算。
- 每次编码后调用 `discardChanges()`，变更队列才会清空——漏调会让旧变更反复进补丁。
- 每轮都新建 state/encoder/decoder，`best of N` 取最低总耗时，避免 GC 抖动。
- 校验：每轮解码后遍历 2000 人断言 `x` 与期望一致、`y === 20`；方案 A 额外断言首包后
  `player[0].x=15` 而 `player[1]`、`player[1999]` 仍为 `10`。

## 运行

```bash
npm install
npm run bench            # 跑基准，终端打印毫秒/字节，并生成 preview.html
node src/benchmark.mjs --runs 5
node src/benchmark.mjs --no-preview
npm run bench:bad        # 复现 7950 万字节的失败形态
npm run bench:inspect    # 查看首包字节、尺寸分布、JSON/msgpack 全量快照对比
```

`preview.html` 只画第一个人和最后一个人的坐标 `(15, 20)`（外加起点 `(10, 20)` 的虚影），
并附三种模式的指标表；不做 2000 个点的动画。
